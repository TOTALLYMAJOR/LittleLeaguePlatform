# Exceptional UX Acceptance Audit

This audit translates the desired LeaguePilot experience into acceptance criteria and checks whether the current repo has matching functionality. Status labels:

- `Covered`: functionality exists in route, service/domain logic, and focused tests or proof scripts.
- `Partial`: functionality exists, but production proof, hosted browser evidence, provider wiring, or a deeper workflow remains open.
- `Gated`: intentionally present only as records, drafts, proof, or disabled provider paths until explicit production gates pass.
- `Not covered`: no meaningful implementation found.

## Global Done Standard

LeaguePilot is done when a real league can run a season without the app leaking family data, confusing volunteers, or implying unproven provider/payment behavior.

Acceptance criteria:

- Every private route derives access from a verified Supabase session and enforces parent, coach, or admin role scope server-side.
- Every sensitive mutation validates actor authority in a Supabase adapter or service, not only in the UI.
- Parent, coach, admin, caregiver, and sponsor workflows expose loading, empty, success, failure, and denied states where the route can fail.
- Registration, invite, guardian, caregiver, provider, payment, moderation, archive, and admin actions are auditable.
- Email, SMS, push, Stripe, AI publishing, media uploads, and provider rendering remain separated from local UI proof until the relevant sandbox, webhook, consent, and hosted gates pass.
- Mobile and desktop browser proof exists for user-visible route changes before claiming visual completion.

Current coverage: `Partial`. The route, service, RLS, migration, QA-script, and test scaffolding are broad, but several production proof lanes remain open: signed-in hosted proof for some flows, live provider delivery, Stripe settlement, private media storage/scanning, Realtime proof, backup/PITR/restore acceptance, and some cross-tenant lifecycle proof.

## What Does Not Yet Exist As Production-Ready Functionality

- Live external email/SMS/Web Push delivery to families.
- Live Stripe sponsor payment collection or webhook-confirmed settlement claim.
- Production-enabled private media upload/release with scanner and storage proof.
- Native Expo app.
- Fully proven production Realtime behavior.
- Full hosted proof for every admin, coach, parent, caregiver, media, sponsor, and season-transition lifecycle.
- Backup/PITR/restore acceptance for production launch.

## Next Acceptance Slices

1. Close hosted proof for the highest-trust flows: registration approval, media report/moderation, tenant readiness, and admin team-builder publish.
2. Decide whether sponsors remain proof-only or whether Stripe sponsor collection becomes an approved sandbox slice.
3. Finish provider-delivery proof only with a consenting QA allowlist recipient, callback reachability, signed webhook replay, cost controls, and monitoring.
4. Promote private media only after scanner, storage RLS, consent, release, and deletion proof are available.
5. Run production role/browser and RLS proof across parent, coach, admin, caregiver, and public surfaces before calling the full app launch-ready.
